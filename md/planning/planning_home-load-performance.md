# 홈 로드 성능 개선 기획

## 문제 정의

하단 네비게이션에서 `마이` 탭에 있다가 `학식`, `셔틀`, `핀`을 누르면 단순 탭 전환처럼 보여야 하지만 실제로는 홈 페이지(`/?panel=...`)로 이동하면서 홈 서버 로드가 다시 실행된다.

현재 홈 로드는 패널 종류와 관계없이 아래 작업을 수행한다.

- 학식 메뉴 캐시 확인 또는 크롤링
- 학식 메뉴 DB 동기화
- 푸드코트 메뉴 DB 동기화
- 홈 지도 데이터 조회
- 학식 평가 데이터 조회

그 결과 셔틀이나 핀처럼 학식 데이터가 당장 필요 없는 화면에서도 학식 관련 작업을 기다리게 된다. 특히 개발 환경처럼 KV 캐시가 없는 경우 `getTodayMenuWithRefresh`가 직접 크롤링으로 떨어질 수 있어 체감 지연이 커진다.

## 목표

- `셔틀`과 `핀` 진입은 학식 메뉴, 학식 평가, 학식 DB 동기화를 기다리지 않는다.
- `학식` 진입은 식단 데이터가 필요하므로 메뉴 조회는 유지하되, 반복 요청에서 같은 식단을 다시 크롤링하지 않도록 한다.
- DB 동기화는 화면 표시보다 뒤에 처리해 첫 화면 응답을 막지 않는다.
- 기존 홈 화면, 학식 바텀시트, 셔틀 바텀시트, 핀 준비 중 바텀시트의 사용자 동작은 유지한다.

## 접근 방식

### 1. 패널별 로드 정책 분리

홈 서버 로드 초기에 `panel` 쿼리 값을 기준으로 로드 정책을 만든다.

- `panel=shuttle`
  - 학식 메뉴 조회 생략
  - 학식 평가 조회 생략
  - 학식 DB 동기화 생략
  - 지도, 카테고리, 구역, 셔틀 기본 데이터만 로드
- `panel=pin`
  - 학식 메뉴 조회 생략
  - 학식 평가 조회 생략
  - 학식 DB 동기화 생략
  - 지도, 카테고리, 구역, 장소 데이터만 로드
- `panel=cafeteria` 또는 기본 홈
  - 학식 메뉴 조회 유지
  - 학식 평가 조회 유지
  - DB 동기화는 백그라운드 처리

### 2. 로컬/서버 메모리 식단 캐시 추가

Cloudflare KV가 있는 운영 환경에서는 기존 KV 캐시를 사용한다. KV가 없는 로컬 개발 환경이나 일반 Node 실행 환경에서는 모듈 메모리에 주간 식단을 임시 저장한다.

- 현재 주 식단이 메모리에 있으면 즉시 반환한다.
- 오래된 식단만 있으면 우선 오래된 식단을 반환하고 백그라운드 갱신을 시도한다.
- 메모리에도 식단이 없을 때만 직접 크롤링을 수행한다.

이 방식은 `마이 -> 학식`처럼 같은 개발 세션에서 다시 홈으로 돌아올 때 반복 크롤링을 막는다.

### 3. 동기화 작업 백그라운드화

홈 화면을 그리는 데 필요한 데이터와 DB 정합성 동기화를 분리한다.

- 메뉴를 화면에 보여주는 데 필요한 `weeklyMenu`는 서버 로드 결과에 포함한다.
- `ensureWeeklyCafeteriaMenu`, `syncFoodCourtMenu`, `syncWeeklyCafeteriaMenu`는 가능하면 `platform.context.waitUntil`에 맡긴다.
- `waitUntil`이 없는 로컬 환경에서는 `void Promise`로 실행하고 오류만 로깅한다.

- 별도 API로 학식 평가를 클라이언트에서 나중에 불러오는 구조
- 홈 지도 데이터를 완전히 클라이언트 캐시하는 구조
- 네이버 지도 SDK 로딩 최적화
- 페이지 전환 애니메이션 최적화

## 검증 기준

- `panel=shuttle`과 `panel=pin`에서는 학식 메뉴 조회와 평가 조회가 실행되지 않는 정책 테스트가 통과한다.
- `panel=cafeteria`와 기본 홈에서는 학식 메뉴와 평가 조회가 유지된다.
- `npm test`가 통과한다.
- `npm run check`가 오류와 경고 없이 통과한다.
