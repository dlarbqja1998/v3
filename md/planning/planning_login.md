# 로그인 및 하이브리드 온보딩 기획

## 목표

골라바유 v3에서는 v2에서 사용하던 카카오 로그인 앱 키를 그대로 사용하되, 회원 데이터와 온보딩 데이터는 v3 데이터베이스 기준으로 새롭게 적재한다.

사용자는 기존 골라바유와 동일한 서비스라고 인식하므로 카카오 로그인 앱을 새로 만들기보다 기존 카카오 Developers 앱을 재사용한다. 대신 v3에서는 신규 온보딩 플로우를 적용해 닉네임, 단과대, 학과, 학번, 성별 정보를 다시 받는다.

## 기본 방향

- 카카오 로그인은 v2에서 사용하던 카카오 Developers 앱을 재사용한다.
- `C:\golabau\.env`에 있는 카카오 로그인 관련 환경변수를 그대로 사용한다.
- 비밀 키 값은 문서나 코드에 직접 노출하지 않는다.
- v2 회원 데이터베이스는 가져오지 않고, v3 데이터베이스에 새 사용자로 적재한다.
- 같은 카카오 계정으로 로그인하더라도 v3 데이터베이스에 사용자가 없으면 신규 사용자로 생성한다.
- 신규 사용자는 하이브리드 온보딩을 완료해야 앱의 주요 로그인 기능을 사용할 수 있다.

## 사용 환경변수

현재 `C:\golabau\.env`에 있는 아래 환경변수를 사용한다.

- `AUTH_KAKAO_ID`
- `AUTH_KAKAO_SECRET`
- `AUTH_URL`
- `AUTH_SECRET`

운영 배포 시에는 기존 카카오 Developers 앱에 v3 운영 도메인의 Redirect URI를 추가해야 한다.

로컬 개발 시에는 아래 Redirect URI를 카카오 Developers에 등록한다.

```text
http://localhost:5173/auth/callback/kakao
```

운영 배포 시에는 실제 서비스 도메인을 기준으로 아래 형태를 등록한다.

```text
https://서비스도메인/auth/callback/kakao
```

## 로그인 진입 흐름

로그인이 필요한 상황은 우선 아래 기능으로 잡는다.

- 글쓰기
- 핀 찍기
- 포인트샵
- 문의하기
- 만나볼텨
- 추후 사용자 식별이 필요한 기능

사용자가 로그인되지 않은 상태에서 위 기능에 접근하면 `/login`으로 이동한다.

`/login` 화면에는 메인 CTA로 `카카오톡 3초 로그인하기` 버튼을 둔다. 사용자가 이미 카카오 계정에 로그인되어 있으면 카카오 계정 입력 화면을 거의 거치지 않고 바로 인증이 완료된다.

단, v3 입장에서는 처음 방문한 사용자를 자동으로 알 수 없으므로 최초 1회는 반드시 카카오 로그인 버튼을 눌러 OAuth 흐름을 시작해야 한다.

## 카카오 로그인 처리 흐름

1. 사용자가 `/login`에서 `카카오톡 3초 로그인하기`를 누른다.
2. 카카오 OAuth 인증 페이지로 이동한다.
3. 카카오 인증이 완료되면 `/auth/callback/kakao`로 돌아온다.
4. 서버는 카카오 사용자 ID를 확인한다.
5. v3 데이터베이스의 `user.providerId`에 같은 카카오 사용자 ID가 있는지 확인한다.
6. 사용자가 없으면 신규 사용자로 생성한다.
7. 신규 사용자의 `isOnboarded` 값이 `false`이면 `/register`로 이동시킨다.
8. 온보딩을 완료하면 v3 데이터베이스의 `user` 테이블에 사용자 정보가 저장된다.
9. 이후 세션 쿠키가 살아있는 동안에는 로그인 상태로 앱을 이용한다.

## 하이브리드 온보딩 항목

온보딩은 아래 순서로 진행한다.

1. 닉네임 설정
2. 단과대 설정
3. 학과 설정
4. 학번 설정
5. 성별 설정

닉네임은 v3 데이터베이스 기준으로 중복을 허용하지 않는다.

단과대 목록은 현재 `src/lib/data/majors.ts`의 데이터를 기준으로 사용한다.

- 공공정책대학
- 과학기술대학
- 글로벌비즈니스대학
- 문화스포츠대학
- 스마트도시학부
- 약학대학
- 크림슨산학융합원(관)
- 그 외

현재 데이터 파일의 `기타` 항목은 사용자 화면에서는 `그 외`로 표현하는 것을 권장한다.

단과대에서 `그 외`를 선택한 사용자는 학과도 `그 외`로 처리한다. 외부인, 졸업생, 교직원, 지역 사용자처럼 고려대학교 세종캠퍼스 소속 학과가 없는 사용자도 자연스럽게 가입할 수 있어야 한다.

## 학번 입력 기준

학번은 실제 전체 학번을 받기보다 `24학번`, `25학번`, `졸업생`, `외부인`, `그 외`처럼 선택형으로 받는 방향을 우선 권장한다.

전체 학번은 개인정보 부담이 크고, 통계와 서비스 분류 목적에는 입학 연도 수준의 정보로 충분할 가능성이 높다.

## 필수 정보 범위

기본 온보딩에서는 아래 정보를 필수로 받는다.

- 닉네임
- 단과대
- 학과
- 학번
- 성별

다만 만나볼텨나 미팅처럼 민감도가 높은 기능에서는 별도 진입 조건을 둘 수 있다. 예를 들어 연락처, 카카오톡 ID, 인스타그램 ID 등은 기본 온보딩에서 강제하지 않고 해당 기능을 사용할 때 추가로 받는 편이 이탈을 줄일 수 있다.

## 관리자 로그인

`/login` 화면 하단에 작고 눈에 덜 띄는 `관리자로 로그인` 진입 버튼을 둔다.

관리자 로그인은 사용자가 직접 아이디와 비밀번호를 입력하는 방식으로 처리한다.

- 관리자 아이디: `golabau`
- 관리자 비밀번호: 서버 환경변수 또는 해시 기준으로 검증
- 관리자 사용자 ID: 1번 계정을 기준으로 처리

관리자 비밀번호는 코드나 문서에 직접 저장하지 않는다. 서버에서는 환경변수로 받은 값을 검증하거나, 가능하면 해시 값으로 비교한다.

관리자 로그인에는 실패 횟수 제한과 짧은 지연 처리를 둔다.

## 데이터 적재 기준

하이브리드 온보딩 완료 시 v3 데이터베이스의 `user` 테이블에 아래 값을 저장한다.

- `nickname`
- `college`
- `department`
- `grade`
- `gender`
- `isOnboarded = true`
- `provider = kakao`
- `providerId = 카카오 사용자 ID`

추후 온보딩 버전 관리가 필요하면 `onboardingVersion` 컬럼을 추가하는 방식을 검토한다. 현재는 v2 데이터베이스를 가져오지 않는 방향이므로 `isOnboarded`만으로도 v3 신규 온보딩 여부를 판단할 수 있다.

## 권한 설계 초안

초기 권한은 단순하게 가져간다.

- 비로그인 사용자: 맛집 탐색, 학식, 셔틀버스, 공지 확인
- 로그인 사용자: 글쓰기, 핀 찍기, 문의하기, 포인트샵, 마이페이지
- 온보딩 완료 사용자: 사용자 기반 기능 전체
- 관리자: 운영 도구, 신고 관리, 콘텐츠 관리

로그인만 필요한 기능과 온보딩까지 필요한 기능은 분리한다.

예를 들어 카카오 인증만 된 상태지만 온보딩이 끝나지 않은 사용자는 `/register`로 보내고, 온보딩 완료 후 원래 하려던 작업으로 돌려보내는 흐름을 추가할 수 있다.

## 남은 결정 사항

- 학번을 선택형으로 받을지, 직접 입력형으로 받을지 확정해야 한다.
- 기존 `grade` 컬럼을 학번 용도로 재사용할지, 별도 `studentYear` 컬럼을 추가할지 결정해야 한다.
- 닉네임 중복 체크를 제출 시점만 할지, 입력 중 실시간 확인 API까지 만들지 결정해야 한다.
- 로그인 후 이동 위치를 항상 `/my`로 할지, 로그인 전 진입하려던 페이지로 복귀시킬지 결정해야 한다.
- 앱 출시 시 Android 패키지명, 키 해시, iOS 번들 ID를 기존 카카오 Developers 앱에 추가해야 한다.

## 1차 구현 범위 제안

1차 구현은 아래 범위로 제한한다.

- 기존 카카오 로그인 환경변수 사용 확인
- `/login` 화면 문구 정리
- `/login` 하단 관리자 로그인 UI 추가
- 관리자 로그인 서버 액션 추가
- `/register`를 단계형 하이브리드 온보딩으로 개편
- 닉네임 중복 검증 추가
- 단과대/학과 목록에 `그 외` 흐름 반영
- 로그인 필요 기능에서 `/login`으로 이동
- 온보딩 미완료 사용자는 `/register`로 이동

이후 핀 찍기와 글쓰기 기능이 구체화되면 `로그인 필요`, `온보딩 필요`, `관리자 필요` 같은 권한 조건을 기능별로 명확히 연결한다.
