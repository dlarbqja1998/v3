# 2026-08-13 개발 로그

## 메인 날씨 위젯 도입

- 고려대학교 세종캠퍼스의 현재 날씨를 메인 지도에서 확인할 수 있는 세로형 위젯을 추가했다.
- 위젯은 바텀시트 최소 단계 바로 왼쪽 위에 고정했다.
- 바텀시트를 중간·최대 단계로 올리거나 학식·셔틀·건물 패널로 전환해도 위젯 좌표가 함께 이동하지 않도록 바텀시트 DOM 밖에 배치했다.
- 위젯 배경은 반투명 흰색으로 구성하고, 날씨 아이콘·기온·상태만 표시했다.
- 로딩 중에는 `--° / 확인 중`, 데이터를 불러오지 못하면 `--° / 확인 불가`를 표시한다.
- 오래된 정상 데이터를 사용하는 경우 화면 표시는 유지하면서 접근성 설명에 `이전 관측 정보`임을 포함한다.

## 호이 날씨 이미지

- 실제 굿즈의 과잠 디자인과 기존 호이 일러스트를 기준으로 날씨 상태별 이미지를 적용했다.
- 다음 여섯 상태를 지원한다.
  - 맑음
  - 구름많음
  - 흐림
  - 비
  - 더움
  - 눈
- 각 이미지는 `static/images/weather` 아래 WebP 형식으로 저장했다.
- 강수 정보가 더움이나 하늘 상태보다 먼저 보이도록 판정 우선순위를 `눈 → 비 → 더움 → 하늘 상태`로 정했다.
- 강수가 없고 현재 기온이 30℃ 이상일 때만 `더움` 호이를 표시한다.

## 기상청 실제 데이터 연동

- 공공데이터포털의 `기상청 단기예보 조회서비스`를 연동했다.
- 초단기실황에서 현재 기온과 강수 형태를 가져오고, 초단기예보에서 가장 가까운 예보 시각의 하늘 상태와 강수 형태를 가져온다.
- 위치는 고려대학교 세종캠퍼스의 기상청 격자 `nx=66`, `ny=107`로 고정했다.
- 한국 시간 기준으로 아직 게시되지 않은 발표값을 요청하지 않도록 안전 여유를 적용했다.
  - 초단기실황: 매시 40분 이후 현재 시각 정시 자료 사용
  - 초단기예보: 매시 45분 이후 현재 시각 30분 자료 사용
- 기상청 원본 응답을 골라바유 공개 응답으로 정규화하는 `/api/weather/current` 경로를 추가했다.
- 외부 요청에는 5초 제한을 적용하고, 원본 오류나 인증정보가 사용자 응답에 포함되지 않도록 처리했다.
- 실제 연동 검증에서 세종캠퍼스 날씨 `29° / 흐림` 응답을 확인했다.

## 캐시와 호출 비용 제어

- 기존 Cloudflare KV 바인딩 `GOLABAU_CACHE`를 재사용했다.
- 캐시 키는 `weather:campus:current:v1`로 지정했다.
- 현재 발표 시각과 캐시의 실황·예보 발표 시각이 모두 같으면 외부 API를 다시 호출하지 않는다.
- 이전 데이터가 6시간 이내이면 우선 `stale: true`로 반환하고 백그라운드에서 갱신한다.
- KV 데이터는 24시간 동안 보관한다.
- 같은 서버 프로세스에서 동시에 갱신 요청이 들어오면 하나의 Promise를 공유하여 중복 기상청 호출을 막는다.
- 별도 날씨 크론과 자동 폴링은 추가하지 않았다.
- 실제 연속 요청에서 같은 `fetchedAt` 값을 반환해 캐시 재사용을 확인했다.

## 웹·모바일 API 경계

- 웹에서는 같은 출처의 `/api/weather/current`를 호출한다.
- Capacitor 앱에서는 `PUBLIC_API_BASE_URL`에 운영 Cloudflare HTTPS 주소를 넣어 같은 API를 호출할 수 있도록 URL 결합 로직을 분리했다.
- HTTP 외부 API 주소와 슬래시로 시작하지 않는 잘못된 경로는 거부한다.
- 기상청 인증키는 `KMA_SERVICE_KEY` 서버 환경 변수로만 읽고 클라이언트 번들에 포함하지 않는다.
- 로컬 `.env`에 개발용 인증키를 설정했지만 `.env`는 Git에서 제외했다.
- 첨부 화면과 대화에 노출된 인증키이므로 운영 배포 전 재발급한 키를 Cloudflare Secret으로 등록해야 한다.

## 관리자 상권 구역 편집 기능

- 기존 `/admin/boundary-editor`를 `캠퍼스 장소`와 `상권 구역` 두 편집 모드로 분리했다.
- 캠퍼스 장소 모드는 기존 `campus_spots` 경계 수정과 공개 지도 캐시 갱신 기능을 유지했다.
- 상권 구역 모드는 `zones` 테이블에 저장된 전체 구역을 표시 순서와 이름 순서로 조회한다.
- 관리자는 목록에서 기존 구역을 선택해 이름과 경계를 수정할 수 있다.
- `새 구역`을 누르면 빈 이름과 빈 경계로 생성 상태를 시작할 수 있다.
- 신규 구역의 첫 세 꼭짓점은 지도 클릭 순서대로 추가하고, 이후 꼭짓점은 가장 가까운 경계선 사이에 삽입한다.
- 꼭짓점은 드래그해 이동하거나 오른쪽 클릭해 삭제할 수 있다.
- 저장 후에는 수정한 구역을 선택한 상태로 관리자 편집 화면을 다시 연다.

## 상권 구역 데이터 처리

- `campus_spots`, `zones`, `places`의 역할을 분리해 기존 학교 건물 데이터와 상권 구역 데이터가 섞이지 않도록 유지했다.
- 음식점 데이터가 아직 없어도 `zones` 구역을 먼저 생성할 수 있다.
- 신규 구역에는 서버에서 UUID를 발급하고 `zone-<UUID 앞 8자리>` 형식의 고유 slug를 생성한다.
- 구역 경계의 최소·최대 위도와 경도를 기준으로 중심 좌표를 계산해 저장한다.
- 신규 구역의 표시 순서는 기존 구역의 마지막 순서 다음 값으로 자동 지정한다.
- 구역 수정은 UUID를 기준으로 처리하므로 이름을 변경해도 새 구역이 중복 생성되지 않는다.
- 이번 작업에는 음식점 핀 생성, 음식점의 구역 배정, 구역 삭제 기능을 포함하지 않았다.

## 입력 검증과 오류 처리

- 구역 이름의 앞뒤 공백을 제거하고 빈 이름을 거부한다.
- DB 컬럼 제한에 맞춰 구역 이름을 80자로 제한한다.
- 같은 이름은 공백과 대소문자 차이를 무시하고 중복으로 판정한다.
- 동일 이름이 있으면 자동으로 덮어쓰지 않고 기존 구역을 선택해 수정하도록 안내한다.
- 경계는 유효한 위도·경도 좌표 세 개 이상일 때만 저장할 수 있다.
- 저장 실패 시 입력하던 이름과 경계 데이터를 유지한다.
- 존재하지 않는 구역 수정은 404 오류로 처리하고 DB 저장 실패는 일반 한국어 오류로 표시한다.
- 관리자 권한 확인과 DB 쓰기는 SvelteKit 서버 액션에서만 수행한다.
